# 데이터 모델 — 초밥 · 손님 · 스테이지 · 점수

## 한 줄 요약

**정적 데이터(SO)와 런타임 상태를 분리**한다. SO 는 읽기 전용 템플릿이고, 게임 중 변하는 값은 별도 클래스에 있다.

출처: [`docs/plan/MVP-milestone.md`](../../docs/plan/MVP-milestone.md) 2차 목표. 여기엔 **원본에 명시된 것 + 구현상 필요해 추가 제안하는 것**을 구분해 적는다.

> 🟢 = 기획 원본에 명시  🔵 = 구현상 필요해 추가 제안 (**승인 필요**)
>
> **수치는 여기 적지 않는다.** 필드가 무엇인지만 정하고 값은 사람이 정한다 (`CLAUDE.md` §7).

## 1. 초밥

### `SushiData` (SO, 정적)

| 필드 | 의미 | |
|---|---|---|
| 가격 | 점수(매출) 기여량이자 타겟팅 우선순위 판별 기준 | 🟢 |
| 포화도 | 손님의 포화도를 채우는 수치 | 🟢 |
| 특성(Trait) | 시너지 키. M3 선택사항 | 🟢 |
| 식별자(Id) | 덱·백과사전·저장에서 참조할 안정적 키 | 🔵 |
| 표시 이름 | UI·백과사전(M6) | 🔵 |
| 스프라이트 | 표현 | 🔵 |

### `SushiItem` (런타임)

| 필드 | 의미 | |
|---|---|---|
| **순차번호(SequenceNumber)** | 스폰 순서. 동일 우선순위 배정의 타이브레이커 | 🟢 |
| 원본 `SushiData` 참조 | 가격·포화도는 여기서 읽는다 | 🔵 |
| 벨트 위 위치 | 진행도 | 🔵 |
| 상태 | `OnBelt` / `Claimed` / `Consumed` — **중복 배정 방지** | 🔵 |
| 배정된 손님 | `Claimed` 일 때 누구에게 | 🔵 |

> **상태 필드가 없으면 두 손님이 같은 초밥을 먹는 버그가 난다.** 배정 확정과 실제 소비 사이에 먹는 시간이 있으므로 그 구간을 표시해야 한다.

## 2. 손님

| 필드 | 의미 | |
|---|---|---|
| 타겟팅 | **단일 가격 값** (TD 의 공격력 대응). 대역이 아니다. **자격 조건이 아니다** (§1.1-3a) | 🟢 |
| 집기 범위 | 벨트 위에서 집을 수 있는 구간 | 🟢 |
| 먹는 시간 | 초밥 1개 소비에 걸리는 시간 | 🟢 |
| 최대 포화도 | 연속 처리를 제한하는 체력 개념 | 🟢 |
| 소화 시간 | 포화 시 휴식 길이 | 🟢 |
| 영입 비용 | 배치 비용 | 🟢 |
| 유형 | 기본 / 소식 / 먹보 (M4). 표시·필터용 | 🔵 |
| 식별자(Id) | 덱·저장 참조 | 🔵 |
| 표시 이름 · 설명 | UI·백과사전(M6) | 🔵 |
| 스프라이트 · 애니메이션 세트 | 표현 (M5) | 🔵 |

> **유형은 로직 분기용이 아니다.** 세 유형은 같은 코드 경로를 타고 값만 다르다 (M4 완료 판정). 유형 필드는 표시·정렬용으로만 쓴다.

## 3. 스테이지

### `StageConfig` (SO, 정적)

| 필드 | 의미 | |
|---|---|---|
| 목표 매출 | 클리어 조건 | 🟢 |
| 제한 시간 | 클리어 조건 | 🟢 |
| **최대 배치 손님 수** | 스테이지 제한 요소 | 🟢 |
| **초기 영입 비용(예산)** | 시작 시 지급 | 🟢 |
| 테이블 배치 | 자리 위치·개수 | 🟢 |
| 벨트 속도 | 초밥 진행 속도 | 🔵 |
| 초밥 스폰 구성 | 어떤 초밥이 어떤 빈도로 나오는가 | 🔵 |
| 보너스 목표 | 추가 보상 조건 | 🔵 |
| 스테이지 번호 · 이름 | 진행 표시 | 🔵 |

### 스테이지 런타임 상태

| 필드 | 의미 | |
|---|---|---|
| 경과 시간 / 남은 시간 | 제한 시간 대비 | 🔵 |
| 현재 매출 | 목표 대비 진행도 | 🔵 |
| 현재 영입 재화 | 초기 예산 + 획득분 − 사용분 | 🔵 |
| 배치된 손님 수 | 최대치 대비 | 🔵 |
| **다음 초밥 순차번호 카운터** | 스폰 시 발급 | 🔵 |
| **다음 손님 순차번호 카운터** | 배치 시 발급 | 🔵 |

> 순차번호 카운터의 **범위(스테이지 단위 리셋 / 런 전체 연속)** 는 결정 필요. 기본안은 스테이지 시작 시 리셋 — 스테이지 간 간섭이 없어 재현이 쉽다.

## 4. 점수 · 경제

**두 개의 다른 자원**이다. 섞지 않는다.

| 자원 | 획득 | 용도 |
|---|---|---|
| **매출(점수)** | 소비된 초밥 가격의 합 | 스테이지 클리어 판정 |
| **영입 재화** | `매출 / 10` (🟢) + 스테이지 초기 예산 | 손님 배치 |

### 미결 — `점수/10` 의 계산 규칙

원본이 공식만 주고 세부를 정하지 않았다. **정하지 않으면 구현이 임의로 고른다.**

- 매 초밥마다 계산해 누적인가, 총매출에 한 번 적용인가?
  - *예: 가격 15 초밥 3개 → 매번 1.5씩(누적 4.5) vs 총 45의 1/10(4.5). 반올림이 끼면 달라진다*
- 정수인가 실수인가? 정수면 **버림 / 반올림 / 올림** 중 무엇인가?
- 소수점 이하를 버린다면 **잔여분을 누적**하는가? (가격 5 초밥을 계속 먹어도 영입 재화가 안 오르는 문제)

**제안**: 실수로 누적하고 **표시할 때만 버림**. 잔여분 손실이 없고 규칙이 단순하다.

## 5. 시너지 버프 (M3, 선택사항)

원본: 특성을 가진 초밥을 처리하면 그 손님에게 **일정 횟수/시간 동안 버프**.

| 필드 | 의미 |
|---|---|
| 버프 종류 | 추가 점수 / 소화 속도↑ / 먹는 속도↑ / 체감 포화도↓ |
| 크기 | 배수 또는 증감치 |
| 지속 | 시간 기반 또는 횟수 기반 |
| 발동 특성 | 어떤 Trait 이 발동시켰나 |

미결:

- 같은 버프가 중첩되나, 갱신되나, 무시되나?
- 버프는 **그 손님에게만**인가, 전체인가? (원본 문구상 해당 손님)
- 시너지 발동 조건 — 특성 초밥 1개면 즉시? 일정 개수 누적?

> **버프가 배정 로직에 영향을 주면 안 된다.** 먹는 속도·소화 속도·체감 포화도는 자격·타이머에 영향을 주지만, **타겟팅 우선순위를 바꾸지는 않는 것**이 기본안이다. 바꾸게 하면 배정 결과가 버프 상태에 따라 흔들려 예측이 어려워진다.
