# 초밥 집기 · 경합 해소 플로우

## 한 줄 요약

초밥이 손님 범위에 **들어오는 순간(이벤트)** 후보로 등록되고, **(손님, 초밥) 쌍을 `대역 밖 거리 → 고가 → 초밥 SeqNo → 대역 폭 → 손님 SeqNo` 로 정렬해** 배정한다. **대역 안이 있으면 즉시, 없으면 최선 후보의 이탈 직전에** 확정한다. **난수는 쓰지 않는다.**

## 핵심 타입 / 진입점

- `SushiDefense.Customers.CustomerLogic` — 자격 판정. **가격 타입을 참조하지 않는다.** `MonoBehaviour` 아님
- `SushiDefense.Customers.ClaimPairComparer` — 정렬 키 5단이 사는 **유일한** 파일
- `SushiDefense.Customers.SushiClaimResolver` — 쌍 랭킹·그리디 배정. **시간을 모른다**
- `SushiDefense.Customers.ClaimDeadline` — "지금 확정할까 기다릴까". **누가 무엇을 가져가는지는 모른다**
- `SushiDefense.Customers.TargetingPriority` — 대역 거리·대역 폭 계산
- 관련 데이터 — [`data-model.md`](data-model.md)

## 1. 자격과 배정을 섞지 않는다

질문이 셋이고, 앞의 하나를 뒤의 둘과 섞는 것이 이 프로젝트에서 가장 흔한 구현 오류다.

| | 질문 | 판정 기준 | 대역 |
|---|---|---|---|
| **자격** | 이 손님이 뭐라도 집을 수 있나 | 범위 ∧ 포화도 여유 ∧ 상태(Idle) | **안 씀** |
| **배정** | 어떤 손님이 어떤 초밥을 가져가나 | 대역 밖 거리 → 고가 → 초밥 SeqNo → 대역 폭 → 손님 SeqNo | 씀 |
| **타이밍** | 지금 확정하나 기다리나 | 대역 안이 있으면 즉시 / 없으면 최선 후보의 이탈 시각 | 씀 |

**자격에 가격이 들어가면 기획 위반이다.** 손님이 눈앞의 초밥을 두고 구경하게 되고, 이건 성능 문제도 밸런스 문제도 아닌 **버그**다.

> **불변식이 M2.5 에서 다시 쓰였다.** 예전 문구 *"가격은 자격에 절대 들어가지 않는다"* 를 문자 그대로는 유지하지 못한다 — 마감시한이 대역을 보고 **언제** 집을지를 바꾸기 때문이다. 대신:
>
> **모든 손님은 유한 시간 안에 반드시 집는다.** 대역은 *무엇을 · 언제* 를 정할 뿐 **영구 배제는 금지**다.
>
> 자격 판정 경로(`CustomerLogic`)가 가격 타입을 참조하지 않는다는 코드 수준의 방어선은 그대로다.

```
집을 수 있다 ⇔ 범위 안에 인식된 초밥이 있다
             ∧ 포화도에 여유가 있다
             ∧ 상태가 Idle 이다 (Eating/Digesting 아님)
```

## 2. 배정 — 쌍(pair) 기반 그리디

기획의 세 경우를 **하나의 규칙**으로 통합한다. 케이스별로 다른 코드를 쓰면 경계에서 반드시 어긋난다.

```
1) 인식된 (손님, 초밥) 쌍을 전부 모은다
     — 손님은 자격을 통과한 손님만
2) 각 쌍을 정렬 키로 랭킹한다
3) 가장 앞선 쌍부터 확정한다
     확정 시 그 손님과 그 초밥을 풀에서 제거
4) 더 이상 쌍이 없을 때까지 3) 반복
```

### 정렬 키 (확정)

| # | 키 | 방향 | 근거 |
|---|---|---|---|
| 1 | 대역 밖 거리 `max(0, min−가격, 가격−max)` | 가까울수록 먼저 | 대역 안은 전부 0 |
| 2 | `초밥 가격` | **높을수록 먼저** | 대역 안 동점을 여기서 깬다 |
| 3 | 초밥 순차번호 | 낮을수록 먼저 | 먼저 나온 초밥 먼저 |
| 4 | **대역 폭** (`max − min`) | **좁을수록 먼저** | 전문가가 범용가를 이긴다 |
| 5 | 손님 순차번호 | 낮을수록 먼저 | 먼저 배치한 손님 먼저 |

**초밥 키(1~3)가 손님 키(4~5)보다 위다.** TD 로 보면 적(초밥)이 최선, 타워(손님)가 차선이다. 순차번호가 유일하므로 이 정렬은 **완전순서**이고, 승자는 항상 하나로 확정된다.

이 한 규칙이 기획의 세 경우를 분기 없이 만족한다:

| 기획 케이스 | 작동하는 키 | 결과 |
|---|---|---|
| 1명 / 1개 | — | 즉시 처리 |
| 1명 / N개 | 1 → 2 → 3 | 4·5는 손님이 하나라 무의미 |
| N명 / 1개 | 1 → 4 → 5 | 2·3은 초밥이 같아 무의미 |
| N명 / N개 | 1 → 2 → 3 → 4 → 5 | 위를 반복 적용 |

### 대역 안은 전부 동점이다 — 그리고 키 2가 그걸 깬다

대역 `100~300` 인 손님에게 150 과 250 은 **거리가 똑같이 0** 이다. 정보를 버리는 것처럼 보이지만 분업이다 — 그 동점을 키 2(고가 우선)가 깨서 250 을 고른다.

이 분업 덕분에 대역이 "선호 구간" 이라는 뜻을 그대로 유지하면서도 점수 최대화 정보를 잃지 않는다. **대역 안에서 FIFO(초밥 SeqNo 순)로 되돌아가면 M2.5 가 없애려던 버그가 한 층 아래에서 재발한다.**

### 대칭성은 대역 '밖' 에 남아 있다

M2.5 가 없앤 것은 **대역 안의** 비대칭 선호("타겟팅 200 이면 199 를 250 보다 먼저")다. 대역 밖에서는 여전히 대칭이다 — 대역 `100~300` 에서 90 과 310 은 **둘 다 거리 10** 이다.

그 동점도 키 2가 310 쪽으로 깬다. 즉 **대역 밖에서는 "가까운 쪽 우선, 같으면 비싼 쪽"** 이 된다. `TargetingPriorityTests.BandDistance_EqualGapOnBothSides_AreEqual` 이 이 성질을 고정한다.

### 대역 폭이 유형을 만든다 — "까다로움" 스탯을 따로 두지 않는다

키 4가 없으면 기본(100~300)과 소식(300~550)이 300 에서 겹칠 때 **배치 순서**가 승자를 정한다. 소식좌가 자기 전문 분야를 먼저 앉은 범용 손님에게 빼앗기는 그림은 M2.5 가 없애려는 "의아함" 과 같은 종류다.

유형 차이도 여기서 나온다. 좁은 고가대 대역은 대역 안 후보가 드물어 **거의 항상 기다리고**, 넓은 저가대 대역은 **거의 항상 즉시** 먹는다. 별도의 인내심 계수(`PatienceRatio`)를 두지 않은 이유이며, 나중에 필요하면 그때 도입한다.

### 순차번호는 보조다 — 어그로 시스템이 아니다

**대역이 항상 순차번호보다 위다.** 배치 순서는 두 손님이 그 초밥을 *똑같이* 원하고 **대역 폭까지 같을 때만** 작동한다.

정렬을 뒤집어(SeqNo 를 타겟팅 위로) "먼저 배치하면 항상 먼저 먹는" 어그로 방식도 가능하지만, **채택하지 않았다.** 손님 유형(소식/먹보)의 정체성이 타겟팅에서 나오는데 SeqNo 를 위로 올리면 그게 지워진다.

> 참고: "소식을 먼저 배치해 포화시키고 먹보가 뒷정리" 같은 전략의 역학은 **순차번호가 아니라 포화도·먹는 속도·범위 겹침**에서 나온다. 순차번호는 "애매한 중간 가격대를 누가 먹느냐" 를 결정하는 좁은 레버다.

### 난수는 쓰지 않는다

순차번호가 모든 동률을 끝내므로 **경합 해소에 난수가 필요 없다.** 같은 판 상태는 항상 같은 결과를 낸다.

- 플레이어에게 일관적이다 — "어떤 때는 앞의 것, 어떤 때는 뒤의 것" 이 사라진다
- 테스트가 쉽다 — 난수원 주입·시드 고정이 **불필요**하다
- 재현이 쉽다 — 버그 리포트의 판 상태만 있으면 그대로 재현된다

> 프로덕션 경합 해소 경로에 `Random` 이 등장하면 규칙 위반이다.

## 3. 인식은 래치된다 (§1.1-3c)

초밥이 손님 범위에 **한 번 들어오면**, 계산이 도는 동안 물리적으로 범위를 조금 벗어나도 **후보에서 빼지 않는다.**

**근거(기획 판단):** 인식은 이미 일어났다. 계산 지연(200ms 내외 허용) 때문에 눈앞에서 놓치는 그림이 나오는 것보다, 인식된 것은 처리되는 편이 플레이 경험이 낫다.

후보에서 빠지는 시점은 이것뿐이다:

- 다른 손님이 그 초밥을 가져감
- 초밥이 벨트에서 제거됨 (라인 끝 도달 → 풀 반납)
- 손님이 자격을 잃음 (포화 → `Digesting`)

**상한이 있다 (M1 에서 결정).** `StageConfig.RecognitionLatchSeconds` 가 지나면 후보에서 만료된다 — 상한이 없으면 한참 지나간 초밥까지 집는 그림이 나온다. 그래서 후보에서 빠지는 경우는 위 셋에 **만료**를 더해 넷이다.

### 기준은 인식 시각이 아니라 **이탈 시각**이다 (M2.5)

```
만료 ⇔ now − 이탈시각 > 래치        (M2.5 이후)
만료 ⇔ now − 인식시각 > 래치        (M1·M2)
```

M1 의 인식 기준 계산은 **`래치 ≥ 범위 통과 시간` 일 때만** §1.1-3c 의 의도와 일치하는 근사였다. stage01 은 통과 시간이 `2 × reach 3 / speed 2 = 3.0초` 인데 래치가 `1.0초` 라 그 조건을 어겼고, **범위 안에 멀쩡히 있는 초밥이 인식 1초 뒤 후보에서 빠졌다.**

이탈 기준으로 바꾸면 얻는 것이 하나 더 있다:

> **마감시한(`now ≥ 이탈`)이 만료(`now > 이탈 + 래치`)보다 항상 먼저 온다.**
> 래치가 `> 0` 이면 둘 사이에 래치만큼 여유가 있고, `0` 이면 만료 자체가 없다.
> 그래서 §5 의 불변식이 **밸런스 값과 무관하게** 성립한다.

부수 효과로 `CandidateSet` 이 시계를 갖지 않아도 된다 — 인식 시점의 "지금" 을 받을 이유가 사라지고, 기하로 정해진 이탈 시각 하나면 충분하다.

> **`0` 은 "상한 없음" 이다.** "이탈 즉시 만료" 가 아니다 — 그렇게 구현하면 마감시한과 같은 틱에 후보가 사라져 손님이 굶는다. 구현은 `SushiDefense.Customers.CandidateSet`.
>
> 재인식은 **이탈 시각을 갱신하지 않는다.** 기하로 정해진 값이라 다시 계산해도 같아야 한다.

### 래치와 마감시한은 역할이 다르다

| | 역할 |
|---|---|
| **마감시한** (이탈 시각) | *언제 결정하나* — 범위 안에 있는 동안 결정한다 |
| **래치** (`RecognitionLatchSeconds`) | *결정이 한 틱 늦어도 유효하게* — 계산 지연 안전망 |

**남은 취약점 하나**: 한 프레임이 래치보다 길면(`delta > 래치`) 같은 틱에 만료가 먼저 일어나 초밥을 잃는다. 프레임이 래치보다 긴 상황은 이미 병적이라 틱 순서를 바꾸지 않았다.

## 4. 탐색은 이벤트 기반 (§1.1-3c)

**매 프레임 전체 초밥을 스캔하지 않는다.** 손님 수 × 초밥 수 검사가 매 프레임 도는 구조는 WebGL 프레임 예산을 그대로 먹는다.

### 구현 선택지 — 결정적 구간 계산 채택

| | A. 2D Trigger 콜라이더 | **B. 결정적 구간 계산 (채택)** |
|---|---|---|
| 방식 | 손님마다 범위 트리거, `OnTriggerEnter2D` | 벨트가 1차원·등속이므로 진입 시각을 **계산**해 타임라인에 넣는다 |
| 물리 엔진 | 필요 | **불필요** |
| 테스트 | PlayMode 필요 (콜백이 `MonoBehaviour` 에 묶임) | **EditMode 로 전부 검증** |
| 결정성 | 물리 틱 의존 | 완전 결정적 |

**B 를 채택했다.** 벨트는 1차원 라인이고 초밥은 등속이라 진입 시각이 위치·속도만으로 나온다 — 물리 엔진이 할 일이 없다.

진짜 이유는 성능보다 **`CLAUDE.md` §3.2 정합성**이다. A 는 판정 트리거가 `MonoBehaviour` 콜백 안에 있어 로직이 끌려들어가고 EditMode 테스트가 막힌다. B 는 진입 계산과 배정이 전부 순수 클래스다. §3-래치 규칙과도 잘 맞는다 — 래치는 "이벤트로 등록된 것을 유지"하는 것이라 물리 이탈 판정에 의존하지 않는 편이 단순하다.

### 재배정이 필요한 순간

- 초밥이 어느 손님 범위에 **진입**
- 초밥이 **소비됨** (다른 손님이 가져감) → 남은 손님 후보에서 제거
- 초밥이 **벨트에서 제거됨** (라인 끝)
- 손님이 `Eating` → `Idle` 전이 (다시 자격 획득)
- 손님이 포화 → `Digesting` 전이 (자격 상실)
- **손님이 새로 배치됨** (스테이지 진행 중 배치를 허용하는 경우)
- **마감시한 도달** — 기다리던 손님의 최선 후보가 범위를 벗어날 시각이 됐다 (M2.5)

배정은 매 틱 돌지만, 실제로 확정되는 손님은 `ClaimDeadline` 이 걸러 낸다.

### 구성 제약 — 집기 범위가 벨트를 넘으면 안 된다

```
자리 벨트좌표 + Reach  <  벨트 길이        (모든 자리)
```

이걸 어기면 **기다리는 손님이 굶는다.** 초밥이 범위를 벗어나기 전에 벨트 끝에서 사라져 마감시한이 영영 오지 않기 때문이다. 즉시 확정이던 M2 까지는 발생할 수 없던 조건이라 M2.5 에서 새로 생겼다.

`Stage01SceneTests.Play_Scene_ReachStaysInsideBelt` 가 이 제약을 잠근다.

## 5. 기획 의도

- **구경하는 손님을 만들지 않는다.** 타워 디펜스에서 "사거리 안 적을 놔두는 타워"는 고장으로 읽힌다. 대역을 자격 조건으로 쓰면 정확히 그 그림이 나온다. **기다리는 것과 구경하는 것은 다르다** — 기다림은 유한하고 반드시 끝난다.
- **대역은 배치 전략의 재료다.** 어떤 손님을 어디에 앉히느냐가 의미를 가지려면, 대역이 "못 먹게 하는 것"이 아니라 "겹쳤을 때 누가/무엇을 가져가느냐"를 정해야 한다.
- **기다림에는 비용이 있다.** 유예 중인 손님은 그 초밥에 대한 지분이 없어, 다른 손님이 가져갈 수 있다. 대기에 아무 위험이 없으면 대역이 좁은 손님이 일방적으로 유리해진다.
- **순차번호는 일관성을 위한 것이다.** 같은 상황에서 매번 다른 결과가 나오면 플레이어는 규칙을 배울 수 없다.

## 6. 왜 대역인가 — 그리고 단일 값을 반대했던 논증은 어떻게 해소됐나

**M2 까지는 단일 가격이었다.** M2.5 가 대역으로 뒤집었다. 당시 대역을 반대한 논증을 지우지 않고 남긴다 — 지우면 다음 사람이 같은 반대를 처음부터 다시 발명한다.

### 바꾼 실제 이유는 가독성이다

*"타겟팅 200 인 손님은 199 를 250 보다 먼저 집는다"* 는 규칙은 플레이어에게 **설명을 듣고도 예측되지 않는다.** 타겟팅이 공격력이자 캐릭터 특성으로 소개되는데 정작 우선순위 계산용으로만 쓰이는 것이 괴리의 근원이었다.

기준선 측정이 이걸 숫자로 확인했다 — 경합이 없는 조건에서도 타겟팅 300 인 손님이 먹은 것의 **81%가 300 미만**이었다 ([`design/m2-5-targeting-band/baseline.md`](../../design/m2-5-targeting-band/baseline.md)).

### 반대 논증 둘과 그 해소

| 당시 반대 근거 | 어떻게 해소됐나 |
|---|---|
| *"대역 안은 전부 동점이 되어(205 와 250 이 같음) 점수 최대화 게임에서 정보를 버린다"* | **정렬 키 2(고가 우선)가 그 동점을 깬다.** 대역은 "선호 구간" 의 뜻을 유지하고, 그 안의 우열은 가격이 정한다 (§2) |
| *"손님마다 폭이 달라 «거리 10» 의 의미가 서로 다르다 → 폭으로 나눠 정규화해야 하고, 그 방식이 곧 전문가 vs 범용가 파워 밸런스가 되어 결정이 하나 더 늘어난다"* | **폭으로 나누지 않는다.** 폭 자체를 이산 타이브레이커(키 4)로 쓰면 정규화가 필요 없다. 대역 밖 거리는 손님과 무관하게 언제나 같은 단위(엔)다 |

> `TargetingPriority` 에 `/ 폭` 이 등장하면 위 해소가 무너진 것이다. 설계 위반으로 취급한다.

### 대역이 데려온 새 문제 하나

단일 값 시절에는 없던 실패 모드가 생겼다 — **기다리다 굶는 경우**다. 두 겹으로 막았다:

1. 래치를 이탈 기준으로 바꿔 마감시한이 만료보다 항상 먼저 오게 했다 (§3)
2. 집기 범위가 벨트를 넘지 않도록 구성 제약을 씬 테스트로 잠갔다 (§4)

## 7. 알려진 제약 / 미결

**미결이 남아 있지 않다.** M2 에서 마지막 하나가 닫혔고, M2.5 는 새 미결을 만들지 않았다.

결정된 것:

- **타겟팅 = 대역, 확정 = 마감시한** (M2.5). 유예 시간(초) SO 필드는 **없다** — 기하로 계산된다
- **인내심 계수(`PatienceRatio`)를 도입하지 않는다** (M2.5). 대역 폭과 스폰 희소성 α 가
  이미 유형을 차별화한다. 필요해지면 그때 넣는다

- **순차번호 범위 = 스테이지마다 리셋** (M2). `StageBootstrap.Build()` 가 호출마다 발급기를
  새로 만든다. 스테이지 2·3 의 배정 결과를 되짚는 데 앞 스테이지 이력이 필요 없다

- **인식 래치 상한 = 시간 상한** (M1). `StageConfig.RecognitionLatchSeconds`, 0 이면 상한 없음 → §3
- **한 손님은 한 번에 하나만 집는다** (M1). `SushiClaimResolver` 가 배정당 손님 하나를 한 번만 확정한다
- **계산 예산 200ms 내외까지 UX 허용** (사용자 판단). 이보다 커지면 재검토
- **재배치는 MVP 범위 밖.** 순차번호 재발급 문제를 지금 다루지 않는다

### 가격을 읽는 곳은 다섯뿐이다

자격 판정에 가격이 새는 것이 이 시스템의 최대 위험이라, 가격을 읽는 지점을 셀 수 있게
유지한다. `CustomerLogic.cs` 와 `CustomerAppetiteMachine.cs` 에 `Price`·`Targeting` 이
등장하면 규칙 위반이다.

| 파일 | 무엇을 위해 |
|---|---|
| `Belt/SpawnShareTable` | 등장 빈도 `(덱 내 최저가/가격)^α` |
| `Customers/TargetingPriority` | **대역 산술 — 거리와 폭. 계산식이 사는 유일한 곳** |
| `Customers/ClaimPairComparer` | 위 값을 정렬 키로 (계산식은 갖지 않는다) |
| `Customers/ClaimDeadline` | 최선 후보가 대역 안인지 (계산식은 갖지 않는다) |
| `Customers/ClaimCoordinator` | 소비 시점에 매출·재화로 넘김 |

`tests/preflight.sh` 가 이 표를 **허용 목록으로 강제한다** — `BandDistance`·`BandWidth`·
`TargetingMin`·`TargetingMax` 가 위 세 파일 밖에 등장하면 FAIL 이다.

### 소비 시점 — M2 에서 바뀐 것

M1 은 **배정 확정이 곧 소비**였다. M2 는 그 사이에 먹는 시간이 있다.

```
배정 확정 → Eating 진입. 초밥은 Claimed 로 벨트에 남는다
   ↓ eatSeconds 경과
소비 확정 → 포화도 · 매출 · 재화 · 벨트 제거
```

**먹다 만 초밥이 끝점을 지나면 놓친다.** 의도된 동작이다 — 손님은 `AbortEating` 으로
`Idle` 에 돌아오고 매출은 붙지 않는다.

### 틱 순서가 계약이다

`ClaimCoordinator.Tick` 의 6단계 순서는 바꾸면 안 된다.

```
1) 벨트   2) 식욕 진행 + 소비 확정   3) 진입 인식
4) 래치 만료   5) 자격 정리   6) 배정
```

- **2 가 5·6 보다 앞**이어야 먹기·소화를 마친 손님이 같은 틱에 자격을 되찾는다. 뒤에 두면
  손님이 매번 한 틱씩 굶는다
- **1 이 3 보다 앞**이어야 이미 내려간 초밥이 같은 틱에 인식되는 유령 배정이 없다
- **4 가 6 보다 앞**이어야 래치 상한이 의미를 갖는다

M2.5 이후 4와 6의 순서는 **결과를 바꾸지 않는다.** 마감시한이 만료보다 구조적으로 먼저
오기 때문이다 (§3). 순서는 그대로 두되, 그 이유가 바뀌었다는 것을 알고 있어야 한다.
