# 스테이지와 런 — 클리어 판정 · 재시도 · 보상

한 판이 **끝나는** 구조가 어떻게 돌아가는지. 무엇을 만들지는 [`docs/plan/M3-stage-and-roguelite.md`](../../docs/plan/M3-stage-and-roguelite.md)에 있고, 여기엔 **왜 이렇게 돌아가는가**를 남긴다.

---

## 1. 판정 규칙 — 매출을 먼저 본다

```csharp
if (revenue >= targetRevenue) return StageOutcome.Cleared;
return expired ? StageOutcome.Failed : StageOutcome.InProgress;
```

**제한 시간 정각에 목표를 채우면 클리어다.** 순서를 뒤집어 만료를 먼저 보면 같은 프레임에 목표를 채운 플레이어가 실패한다.

이 두 줄이 `StageEvaluator` 의 전부이며 **시간을 모른다** — 만료 여부를 `bool` 로 받는다. 그래서 경계 규칙을 시계 없이 고정할 수 있고, `Evaluate_TargetReachedExactlyAtTimeout_Clears` 하나가 결정을 지킨다.

> 분기가 셋 이상이 되면 규칙이 새로 생긴 것이다. **보너스 목표(`StageConfig.BonusObjectives`)는 여기 들어오지 않는다** — 추가 보상 조건이지 클리어 조건이 아니다.

## 2. 틱 계약 — **판정은 조율자 뒤에**

`StageController.Tick` 의 순서:

```
0) 이미 끝났으면 조기 반환
1) 조율자를 굴린다
2) 시계를 흘린다
3) 판정한다
```

**지켜야 하는 것은 "3이 1 뒤" 하나다.** 앞서 판정하면 이번 프레임에 입에 들어간 초밥의 매출이 빠진 채로 만료가 걸려 *"먹었는데 실패"* 가 난다.

**1과 2의 상대 순서는 관측되지 않는다.** 조율자는 시계를 읽지 않고 시계는 매출을 읽지 않으므로, 판정이 두 최종값을 읽는 한 어느 쪽을 먼저 굴려도 결과가 같다 — 실제로 바꿔 넣어도 전량 통과했다.

> M3 착수 시 작업서에는 "조율자 → 시계 → 판정" 3단 전체가 계약이라고 적혀 있었다. **주입 실험으로 틀렸음이 드러나 정정한 서술이다.** 지킬 필요 없는 순서를 계약으로 알면, 정작 지켜야 할 것을 놓친다.

## 3. 판정 후에는 멈춘다

결과가 난 뒤 조율자를 틱하지 않는다. 안 그러면 보상 화면 뒤에서 벨트가 계속 흐르며 매출이 오른다.

`Tick` 맨 앞의 조기 반환 하나가 이것과 **"`OutcomeDecided` 는 판당 한 번"** 을 동시에 보장한다. 별도의 발행 플래그를 두지 않는 이유다 — 두 장치가 같은 것을 지키면 나중에 한쪽만 고쳐진다.

정지 테스트에는 반드시 **대조군**이 필요하다. 초밥이 한 개도 안 나오는 하네스에서는 "멈췄다" 가 공허하게 통과한다.

## 4. 런의 수명 — `Build()` 바깥에 산다

| 재시도 시 | |
|---|---|
| **살아남는 것** | 초밥 덱 · 손님 명부 · 스테이지 번호 · 시도 횟수 · 난수원 |
| **새로 열리는 것** | 매출 원장 · 영입 지갑 · 벨트 · 조율자 · 순차번호 발급기 · 스테이지 컨트롤러 |

`StageBootstrap.Build()` 는 호출마다 뒤쪽을 전부 새로 만든다(M2 확정 — 스테이지 간 이월 없음). `RunState` 만 `??=` 로 한 번만 만들면 **재시도에 새 코드가 거의 없다** — `Retry()` 는 `RecordFailedAttempt()` + `Build()` 두 줄이다.

**실패해도 런은 끝나지 않는다** (M3 착수 시 확정). 같은 스테이지에 머물고 시도 횟수만 오른다. 정통 로그라이트라면 런 종료지만, 3스테이지 데모에서는 한 번의 실패가 곧 전체 리셋이라 체감 난도가 급격히 오른다.

> `RunState` 는 **Unity API 를 모른다.** SO 참조만 담으므로 나중에 저장이 필요해지면 `SushiData.Id`·`CustomerData.Id` 로 매핑하는 계층만 얹으면 된다. 지금 Id 기반으로 짜지 않는 이유는 쓰지 않을 간접층이기 때문이다 (플랜 Q1 — 메모리만 유지).

## 5. 덱의 진실이 옮겨 갔다

**`StageConfig.SpawnTable` 은 이제 런의 *시작 덱* 이다.** 벨트는 주입받은 초밥 목록을 읽는다.

M2 까지 `SushiBelt` 는 생성자에서 `config.SpawnTable` 을 직접 읽었는데, 그대로 두면 **보상으로 얻은 초밥이 영영 벨트에 나오지 않는다.** 래퍼(`SushiSpawnEntry`)를 벗기는 일은 `SushiDeck.FromSpawnTable` 한 곳으로 모았고, 래퍼 자체는 인스펙터 쪽에 그대로 남는다 — "덱의 슬롯" 이라는 의미가 있어 존재하는 타입이다.

> 다음에 스폰 구성을 만질 때 **SO 를 직접 읽고 싶어지면 이 절을 다시 본다.**

## 6. 난수의 경계 — 배정에는 없다, 보상에만 있다

| 경로 | 난수 |
|---|---|
| 배정 (누가 무엇을 먹나) | **없다.** 순차번호가 모든 동률을 끝낸다 |
| 스폰 (무엇이 얼마나 나오나) | **없다.** credit 누적이 순서를 만든다 |
| **보상 추첨** | **있다.** 주입된 `IRandomSource` |

전역 난수(`UnityEngine.Random`·`System.Random`)는 `Runtime` 어디에서도 쓰지 않는다. 시드를 우리가 들고 있지 않으면 같은 런을 다시 돌려볼 수 없고, 보상 테스트가 값 비교가 아니라 통계 검증이 된다. 시드를 만드는 곳은 `StageBootstrap.NewSeed()` **한 곳뿐**이다 (`Presentation` 이라 전역 난수가 허용된다).

`tests/preflight.sh` 가 두 항목으로 지킨다:

- **배정 난수 금지** — `Runtime/Run/` 허용 목록 밖의 `Random` 을 FAIL
- **전역 난수 금지** — 허용 목록 안에서도 `UnityEngine.Random`·`System.Random` 은 FAIL

> 옛 가드는 `Random\.` 이라는 금지형을 잡아 **`new System.Random()` 을 통과시켰다.** M3 에서 허용 목록 방식으로 바꾸며 그 구멍을 막았다.

### 추첨은 부분 Fisher-Yates

*"인덱스를 무작위로 골라 중복이면 다시"* 방식은 루프 횟수가 뽑힌 값에 따라 달라져 **같은 시드로도 소비되는 난수 개수가 흔들린다.** 정확히 `take` 번만 뽑는 부분 셔플을 쓴다. `XorShiftRandomSource` 의 모듈로 편향을 고치지 않는 것도 같은 이유다 — 편향 제거 루프가 같은 문제를 만든다.

## 7. 이미 가진 카드는 제시하지 않는다

스폰 비중이 **가격에서만** 유도되므로(`share ∝ (덱 최저가/가격)^α`, [`spawn-composition.md`](spawn-composition.md)) 중복 카드는 아무 효과가 없다. 손으로 적는 가중치 필드가 없다는 것이 곧 그 뜻이다.

**초밥과 손님을 한 풀에 섞는다.** 종류별 쿼터를 두면 한쪽 풀이 말랐을 때 "몇 개를 제시하나" 가 애매해지고, 그 규칙이 곧 밸런스 손잡이가 되어 SO 필드를 또 부른다.

**후보가 0개여도 화면을 연다.** 조용히 건너뛰면 클리어했는데 아무 화면도 안 뜨는 상태가 되어, 보상 시스템이 고장 난 것과 구분되지 않는다.

## 8. 스테이지 1 밸런스의 근거 (M3 확정)

| 수치 | 값 | 근거 |
|---|---|---|
| 목표 매출 | **5000** | 60초 벨트 총액 6608, 3명 실측 6010, 1명 실측 4170. 1명으로는 못 넘고 3명을 잘 굴려야 닿는다 |
| 제한 시간 | 60초 | M2 에서 확정, 그대로 |
| 보상 풀 (초밥) | 참치 250 · 성게 400 · 달걀 130 | 기존 5종이 전부 시작 덱에 있어 줄 카드가 0개였다 |
| 보상 풀 (손님) | 소식좌 | 씬 명부에 기본만 물려 있어 이미 미보유였다 |
| 제시 개수 | 3 | 풀 4장에서 고르는 재미가 남는다 |

**총액 6608 의 유도**: α=1 에서 `가격 × share` 가 유형마다 같으므로(=`최저가/Σ(최저가/가격)`), 한 번 스폰의 기대값은 `5 × 120/3.6316 = 165`. 60초에 40개가 오르므로 6608.

> 목표를 **6000 이상으로 올리면 이론상 클리어가 불가능**해진다. 3명이 총액의 91%를 먹은 것이 실측 상한이다.

### 아직 안 정한 것

- **소식좌의 영입 비용(40)이 처치량에 비해 비싸다** — M2.5 에서 확인됐고 M9 밸런싱 대상이다. 다만 M3 에서 소식좌가 보상이 되면서 "비용을 내고 사는 것" 이 아니라 "얻는 것" 이 되어 성격이 달라졌다
- **성게 400 은 소식좌 대역(250~320) 밖**이다. 새 상한이 필요한지는 M4(손님 유형)·M9 에서 본다
