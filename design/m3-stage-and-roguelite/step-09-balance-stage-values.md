두 가지를 끝낸다.

1. **값**: 목표 매출과 보상 풀. 지금 상태로는 **실패가 발생할 수 없고 보상으로 줄 카드도 없어서**, 기능은 다 있는데 눈으로 확인할 수가 없다

## 물어볼 것 (1) — 목표 매출: 지금은 실패가 불가능하다

M2 PR #10 에 ⚠️ 로 남기고 M2.5 에서 한 번 더 미룬 항목이다. **M3 에서 처음으로 막힌다** — 클리어/실패 판정을 만들어 놓고 실패가 나오지 않으면 그 코드는 플레이에서 죽어 있다.

측정값 ([`design/m2-5-targeting-band/baseline.md`](../m2-5-targeting-band/baseline.md), 60초):

| 조건 | 매출 | 목표 2500 대비 |
|---|---|---|
| 손님 3명 (S1, M2.5 적용 후) | **6010** | 2.4배 |
| **손님 1명만** (S3, M2.5 적용 후) | **4170** | 1.7배 |

즉 **자리 하나만 채워도 목표를 1.7배로 넘긴다.** 배치·타겟팅·경제 어느 것도 실패로 이어지지 않는다.

| 선택지 | 결과 |
|---|---|
| 목표를 올린다 (예: 5000~5500) | 손님 3명을 제대로 배치해야 클리어. 실패가 실제로 발생한다 |
| 제한 시간을 줄인다 (예: 40초) | 같은 효과. 대신 대기(M2.5)의 손해가 커져 소식좌가 더 불리해진다 |
| 둘 다 그대로 두고 M9 로 또 미룬다 | 판정 코드가 계속 죽어 있다. **테스트는 Green 이므로 코드가 막히지는 않는다** |

> 60초 동안 벨트에 오르는 초밥은 **40개**이고, 그 총액은 이론상 약 7300 이다. 손님 셋이 그중 36개를 가져가 6010 을 만들었다. **목표를 7000 이상으로 잡으면 이론상 클리어가 불가능**하니 상한은 그쯤이다.

## 물어볼 것 (2) — 보상 풀: 지금은 줄 카드가 없다

현재 애셋과 stage01 시작 덱:

| 초밥 애셋 | 가격 | 시작 덱에 있나 |
|---|---|---|
| `Sushi.Squid` (한치) | 120 | ✅ |
| `Sushi.Salmon` (연어) | 150 | ✅ |
| `Sushi.Flounder` (광어) | 150 | ✅ |
| `Sushi.Yellowtail` (방어) | 190 | ✅ |
| `Sushi.Eel` (장어) | 300 | ✅ |

| 손님 애셋 | 영입 비용 | 배치 가능한가 |
|---|---|---|
| `Customer.Standard` (기본) | 20 | ✅ |
| `Customer.SmallEater` (소식) | 40 | ✅ |

**다섯 종 전부 시작 덱에 있고 손님 둘 다 이미 쓸 수 있다.** 미보유 카드가 0개라 보상 화면이 항상 "받을 보상 없음" 을 띄운다.

| 선택지 | 비고 |
|---|---|
| **(a) 시작 덱을 줄인다** — 예: 3종으로 시작하고 방어·장어를 보상 풀로 | 애셋을 새로 만들지 않는다. 대신 **스폰 구성이 바뀌어 (1)의 매출 측정값이 무효**가 된다 |
| **(b) 새 초밥 애셋을 만든다** — 참치·성게 등 | 시작 덱과 매출이 그대로다. 스프라이트 없이 placeholder 아이콘으로 시작 가능. **새 애셋은 §7 승인 사항** |
| **(c) 새 손님 애셋을 만든다** | 손님 유형 확장은 원래 **M4** 다. M3 에서 하면 M4 와 겹친다 |
| **(d) (a)+(b) 혼합** | 시작 덱을 줄이면서 신규도 추가 |

> **(a)는 (1)을 다시 재게 만든다.** 시작 덱이 바뀌면 스폰 구성이 바뀌고 60초 매출이 달라진다. (1)과 (2)를 함께 정한 뒤 한 번에 측정하는 편이 낫다.

`Sushi.Placeholder` · `Customer.Placeholder` 는 **보상 풀에 넣지 않는다.** M0 의 잔재이며 정리 대상이다 (M2.5 에서도 미결로 넘어왔다).

## 물어볼 것 (3) — 제시 개수

`RewardCatalog._offerCount` 기본안은 **3** 이다. 풀이 그보다 작으면 있는 만큼만 제시된다(정상 동작).

## 문서 승격 — `.claude/domain/stage-and-run.md`

계획이 아니라 **"왜 이렇게 돌아가는가"** 를 적는다 (`docs/plan/README.md` §6).

담을 것:

1. **클리어/실패 판정** — `revenue >= target` 을 먼저 본다. 제한 시간 정각에 목표 달성은 **클리어**. 왜 순서가 그런지
2. **틱 순서** — 조율자 → 시계 → 판정. 뒤집으면 "먹었는데 실패" 가 난다. `ClaimCoordinator.Tick` 의 6단계 계약과 같은 성격의 계약이다
3. **판정 후 정지** — 결과가 난 뒤 조율자를 틱하지 않는 이유
4. **런의 수명** — `RunState` 가 `Build()` 바깥에 사는 이유. 재시도 = `Build()` 재호출. 무엇이 살아남고(덱·명부·스테이지 번호) 무엇이 새로 열리는가(원장·지갑·벨트·순차번호)
5. **덱의 진실이 옮겨 갔다** — `StageConfig.SpawnTable` 은 이제 **시작 덱**이다. 벨트는 주입받은 덱을 읽는다. 이걸 모르면 다음 사람이 다시 SO 를 직접 읽는다
6. **난수의 경계** — 배정에는 여전히 없다. 보상 추첨만 예외이고 `IRandomSource` 로 주입한다. 전역 난수 금지. preflight 가드가 어떤 형태로 지키는가
7. **중복 카드를 제시하지 않는 이유** — 스폰 비중이 가격에서만 나오므로 중복이 무효다 ([`spawn-composition.md`](../../.claude/domain/spawn-composition.md) 와 연결)
8. **실패해도 런이 유지된다** — 같은 스테이지 재시도. 이 결정이 밸런스 난도에 주는 영향

## 금지 사항

- **사람 확인 없이 값을 채우지 않는다** (§7). 이 단계의 존재 이유다
- 값이 "명백해 보인다" 는 이유로 건너뛰지 않는다. 위 표의 숫자는 **근거**이지 결정이 아니다
- 사람이 지정하지 않은 필드를 함께 손보지 않는다. M2·M2.5 의 원칙 그대로 — **지정한 부분만 고치고 나머지는 그대로 둔다**
- 새 손님 유형을 만들지 않는다. **M4** 다
- 시너지 관련 애셋·필드를 만들지 않는다. 별도 마일스톤이다 (D8)
- 밸런스가 이상해 보인다고 코드를 고치지 않는다. 값이 잘못된 것과 규칙이 잘못된 것은 다르다 — 후자라고 판단되면 멈추고 보고한다
- 새 계획 문서(`M3.5-*.md` 등)를 임의로 만들지 않는다. 시너지를 어느 마일스톤에 넣을지는 사람이 정한다 — **제안만 남긴다**
- `ProjectSettings/` · `Packages/` · 심링크 공유 폴더를 건드리지 않는다 (RULE-02 · §7)
