# M2.5 — 타겟팅 대역 전환 (기획 변경)

> 원본에 없던 **기획 변경**이다. M2 가 구현한 "타겟팅 = 단일 가격 + 대칭 거리" 를 **"대역 + 마감시한"** 으로 바꾼다.

## 왜 바꾸나

M2 를 실제로 돌려 보고 두 가지가 드러났다.

### (1) 대칭 거리가 플레이어에게 예측되지 않는다

타겟팅 200 인 손님은 **199 를 250 보다 먼저 집는다.** 설계 의도는 "탐욕적이지 않은 선호가 배치 전략을 만든다" 였지만, 플레이어에게 *"이 손님은 200엔대를 좋아한다"* 고 설명한 뒤 이 동작을 보여 주면 규칙을 배우지 못한다. **타겟팅이 공격력이자 특성으로 소개되는데 정작 우선순위 계산용으로만 쓰이는 것**이 괴리의 근원이다.

### (2) "소식좌가 싼 걸 먼저 집는다" — 원인은 FIFO 가 아니다

정렬 키에서 SeqNo 는 3순위다. 후보가 함께 있으면 소식좌는 비싼 쪽을 집는다. 문제는 **후보가 함께 있지 않다는 것**이다.

`ClaimCoordinator.ResolveClaims()` 가 매 틱 **그 순간 인식된 후보만으로** 배정을 확정한다. 싼 초밥이 먼저 범위에 들어오면 후보가 그것 하나뿐이라 **정렬 키가 작동할 기회 자체가 없다.** 손님은 `Eating` 이 되고, 뒤이어 비싼 초밥이 들어올 때는 이미 자격이 없어 후보가 비워진다.

> **즉시 확정(eager commit) 이 진짜 원인이다.** "더 좋은 게 곧 올 텐데 기다릴까" 를 판단하는 장치가 없다.
>
> 이걸 고치지 않으면 대역으로 바꿔도 증상은 그대로다 — 대역을 선호도로만 쓰면 여전히 첫 번째 싼 초밥을 집는다.

## 확정된 규칙

### 자격은 그대로다

```
범위 안  ∧  포화도 여유  ∧  상태(Idle)
```

**가격은 여전히 자격에 들어가지 않는다.** 대역이 자격 게이트가 되면 손님이 영원히 굶는다 — 특히 α=1.0 스폰 규칙에서 비싼 초밥은 의도적으로 희소하므로([`spawn-composition.md`](../../.claude/domain/spawn-composition.md)), 고가 대역 손님의 가동률이 자기 스탯이 아니라 공급률에 묶인다.

### 타겟팅 = 대역, 그리고 마감시한

자격을 통과한 손님에 대해 매 순간:

| # | 조건 | 행동 |
|---|---|---|
| 1 | 후보 중 **대역 안**이 있다 | **즉시 집는다** (여럿이면 가장 비싼 것) |
| 2 | 대역 밖만 있다 | 그중 **가장 좋은 것이 범위를 벗어나기 직전**까지 기다린다 |
| 3 | 그 시각이 됐다 | **집는다** |

**손님별 유예 시간(초) 필드를 두지 않는다.** 마감시한은 그 (손님, 초밥) 쌍의 **범위 이탈 시각**이라 기하로 결정된다 — 벨트가 1차원·등속이므로 `ReachWindow.ExitSeconds` 가 이미 답을 갖고 있다. Reach 가 크면 자연히 길게, 벨트가 빠르면 짧게 스케일한다.

> 고정 길이 타이머는 쓸 수 없다. 유예 시계는 **손님 기준**이고 이탈은 **초밥 기준**이라, 길이를 아무리 잘 맞춰도 둘이 정렬되지 않는다. 통과 시간이 4초일 때 t=3.5 에 인식한 초밥은 t=7.5 에 나가는데 타이머는 t=4.0 에 만료된다.

**가장 좋은 후보가 갱신되면 마감시한도 함께 미뤄진다.** 못한 후보가 먼저 사라지는 것은 손해가 아니다.

### 정렬 키 (5단)

| # | 키 | 방향 | 근거 |
|---|---|---|---|
| 1 | 대역 밖 거리 `max(0, min−가격, 가격−max)` | 가까울수록 먼저 | 대역 안은 전부 0 |
| 2 | 초밥 가격 | **높을수록 먼저** | 대역 안 동점을 여기서 깬다 |
| 3 | 초밥 순차번호 | 낮을수록 먼저 | 먼저 나온 초밥 먼저 |
| 4 | **대역 폭** | **좁을수록 먼저** | **신규** — 전문가가 범용가를 이긴다 |
| 5 | 손님 순차번호 | 낮을수록 먼저 | 먼저 배치한 손님 먼저 |

**초밥 키가 손님 키보다 위**라는 원칙은 유지된다 (1~3 초밥, 4~5 손님). 순차번호가 유일하므로 여전히 **완전순서**다.

키 4 를 넣는 이유: 기본(100-300)과 소식(300-550)이 300 에서 겹칠 때 없으면 **배치 순서**가 승자를 정한다. 소식좌가 먼저 앉은 기본 손님에게 자기 전문 분야를 빼앗기는 그림은 이 변경이 없애려는 "의아함"과 같은 종류다.

### 래치와 역할이 갈린다

| | 역할 |
|---|---|
| **마감시한 (범위 이탈)** | *언제 결정하나* — 범위 안에 있는 동안 결정한다 |
| **`RecognitionLatchSeconds`** | *결정이 한 틱 늦어도 유효하게* — 계산 지연 안전망 (§1.1-3c) |

**래치는 손대지 않는다.** 결정은 범위 안에서 내리고, 래치는 그 결정이 늦어졌을 때를 받쳐 준다.

### 불변식을 다시 쓴다

기존의 *"가격은 자격에 절대 들어가지 않는다"* 를 문자 그대로는 유지하지 못한다. 마감시한은 가격(대역)을 보고 **언제** 집을지를 바꾸기 때문이다. 대신 이렇게 바꾼다:

> **모든 손님은 유한 시간 안에 반드시 집는다.**
> 대역은 *무엇을 · 언제* 를 정할 뿐, **영구 배제는 금지**다.

여전히 테스트로 잠글 수 있다 — `Claim_OnlyOutOfBandSushiInReach_TakesItBeforeExit`.

## 예시 — 소식좌 (대역 300~550)

**비싼 게 온 경우**

| 시각 | 사건 | 손님 |
|---|---|---|
| 0.0 | 자리에 앉음 | 대기 |
| 0.5 | 110엔 인식 (t=4.5 이탈) | 대기 — 마감 4.5 |
| 2.0 | **380엔 인식 → 대역 안** | **즉시 먹기 시작** |

**끝까지 안 온 경우**

| 시각 | 사건 | 손님 |
|---|---|---|
| 0.5 | 110엔 인식 (t=4.5 이탈) | 대기 — 마감 4.5 |
| 1.2 | 150엔 인식 (t=5.2 이탈) | 대기 — **마감 5.2 로 갱신** |
| 4.5 | 110엔 이탈 | 흘려보냄 |
| 5.2 | 150엔 이탈 직전 | **150엔을 먹는다** |

유예가 끝났을 때 집는 것은 **SeqNo 가 빠른 것이 아니라 대역에 가장 가까운 것**이다.

### 유형 차이는 대역 폭에서 나온다

| | 대역 | 실제 행동 |
|---|---|---|
| 먹보 | 100~250 | 싼 초밥이 흔해 규칙 1 로 **거의 항상 즉시** 먹는다 |
| 기본 | 100~300 | 대부분 즉시 |
| 소식 | 300~550 | 대역 안이 드물어 **거의 항상 끝까지** 기다린다 |

**"까다로움" 손잡이를 따로 두지 않아도 차별화가 나온다** — 대역 폭과 스폰 희소성(α)이 이미 만들고 있다. 나중에 필요하면 `PatienceRatio`(0~1, 마감시한 = `진입 + ratio × (이탈 − 진입)`) 하나로 되살릴 수 있다. **처음에는 넣지 않는다.**

## 위치 — M2 후, M3 전

M3 시너지(선택사항)가 *"버프가 배정 우선순위를 바꾸지 않는다"* 를 검증하는데, 그 배정 규칙이 곧 바뀔 거면 두 번 짜게 된다.

플랜상 원래 자리는 M4 다 — 소식/먹보가 실제로 달라져야 하는 마일스톤이고 지금 문제가 정확히 그 지점이다. **M4 에서 앞당겨 온다.**

## 완료 판정

**대역**
- [ ] `CustomerData` 가 타겟팅을 **`min`/`max` 대역**으로 갖는다 (`OnValidate` 에서 `min ≤ max`)
- [ ] 대역 밖 거리가 `max(0, min−가격, 가격−max)` 로 계산된다 — 대역 안은 0
- [ ] **가격을 읽는 지점이 여전히 셀 수 있다** (`TargetingPriority` 한 곳)
- [ ] 정렬 키가 5단이고 **대역 폭이 손님 SeqNo 보다 위**다
- [ ] 대역이 좁은 손님이 넓은 손님과 같은 초밥을 놓고 겨루면 **좁은 쪽이 이긴다**

**마감시한**
- [ ] 대역 안 후보가 있으면 **기다리지 않고 즉시** 집는다
- [ ] 대역 밖만 있으면 **가장 좋은 후보의 범위 이탈 직전까지** 기다린다
- [ ] 더 좋은 후보가 인식되면 **마감시한이 갱신된다**
- [ ] 마감시한이 되면 **대역에 가장 가까운 것**을 집는다 (SeqNo 순이 아니다)
- [ ] 유예 시간(초) SO 필드가 **없다** — 기하로 계산된다
- [ ] `ReachWindow.ExitSeconds` 가 버려지지 않고 후보와 함께 보관된다

**불변식**
- [ ] **범위 안에 초밥이 있는 손님은 유한 시간 안에 반드시 집는다** (영구 구경 0)
- [ ] 자격 판정 경로가 여전히 **가격 타입을 참조하지 않는다**
- [ ] 배정·스폰 경로에 `Random` 0건
- [ ] 같은 판 상태를 두 번 배정하면 결과가 같다 (결정성 유지)

**가시성** — 가독성이 이 변경의 목적이므로 선택이 아니다
- [ ] HUD 가 손님의 **대역**을 보여 준다
- [ ] HUD 가 **기다리는 중** 상태를 구분해 보여 준다

- [ ] EditMode 전량 Green + `/run webgl` 유지

| 파일 | 변경 |

### `Runtime`

| 파일 | 변경 |
|---|---|

## 작업 순서

1. **(선택) 0단계 측정** — 현재 동작의 기준선
2. **`CustomerData` 대역화** (`Runtime.Data`) — 실패 테스트 → 구현
3. **`BandDistance`** (`Runtime`) — 대역 안 0, 밖은 벗어난 만큼
4. **정렬 키 5단** (`ClaimPairComparer`) — 키 4 포함
5. **이탈 시각 보관** (`CandidateSet` · `ClaimCoordinator.Schedule`)
6. **마감시한 필터** (`ClaimDeadline` · `ResolveClaims` 앞)
7. **HUD** (`Presentation`)
8. **문서 일괄 갱신** + preflight 가드 재조준
9. **밸런스 대역 값** — 사람 결정 (§7)

2~4 는 배정 랭킹, 5~6 은 타이밍이라 서로 독립이다. 7 은 그 뒤.

## 테스트 항목

| 대상 | 테스트 이름 예시 |
|---|---|
| 대역 거리 — 안 | `BandDistance_PriceInsideBand_ReturnsZero` |
| 대역 거리 — 밖 | `BandDistance_PriceBelowBand_ReturnsGapToMin` |
| 배정 — 대역 안 고가 우선 | `Resolve_TwoInBandSushi_TakesHigherPrice` |
| 배정 — 전문가 승리 | `Resolve_NarrowBandVsWideBand_NarrowWins` |
| 배정 — 전문가 승리가 배치순을 이김 | `Resolve_NarrowBandPlacedLater_StillWins` |
| 마감 — 대역 안은 즉시 | `Claim_InBandSushiRecognized_ClaimsImmediately` |
| 마감 — 대역 밖은 보류 | `Claim_OnlyOutOfBandSushi_DefersUntilExit` |
| 마감 — 갱신 | `Claim_BetterCandidateRecognized_ExtendsDeadline` |
| 마감 — 만료 시 선택 | `Claim_AtDeadline_TakesNearestToBand` |
| **불변식** | `Claim_OnlyOutOfBandSushiInReach_TakesItBeforeExit` |
| 결정성 | `Resolve_SameBoardTwice_ProducesIdenticalResult` |

**자격과 배정은 여전히 한 테스트에서 같이 검증하지 않는다.** 마감시한 테스트도 자격과 섞지 않는다 — 안 먹은 이유가 자격인지 대기인지 구분되지 않는다.

|---|---|
| **대역이 자격 게이트로 굳는다** | 가장 큰 위험. 완료 판정의 불변식 테스트가 방어선. 희소 공급(α)과 겹치면 손님이 굶는다 |
| 마감시한 판정이 리졸버 안으로 들어간다 | 랭킹과 타이밍이 한 함수가 되면 둘 다 테스트가 어려워진다. 필터로 분리 |
| 대역 안에서 FIFO 를 쓴다 | **지금 고치려는 버그가 한 층 아래에서 재발한다.** 대역 안에서도 키 2(고가 우선)를 유지 |
| 문서만 바뀌고 코드가 안 바뀐다 | 규칙 문서와 구현이 어긋나면 다음 에이전트가 잘못된 쪽을 따른다. **문서 갱신은 코드 커밋과 같은 브랜치에서** |
| 대역이 겹쳐 전문가가 밀린다 | 키 4 가 막는다. 애셋 설계에서도 겹침을 최소화 |
| 소식좌 가동률이 공급률에 묶인다 | 대역 값과 α 를 함께 본다. 영입 비용·최대 포화도를 공급률 대비로 잡는다 (M9) |
