# 개발 플랜 — Sushi Rail Bite

[`MVP-milestone.md`](MVP-milestone.md)(기획 원본)를 실행 가능한 마일스톤으로 옮긴 문서다. **원본은 그대로 두고**, 여기서 순서·의존·완료 판정·산출물을 정의한다.

---

## 0. 이 문서들의 위치

문서 계층이 셋이고, 역할이 겹치면 안 된다.

| 계층 | 위치 | 담는 것 | 만드는 주체 |
|---|---|---|---|
| **기획 원본** | [`MVP-milestone.md`](MVP-milestone.md) | 무엇을 만들 것인가 (사람의 의도) | 사람 |
| **플랜** ← *이 문서들* | `docs/plan/M*.md` | 어떤 순서로, 무엇이 끝나야 끝난 것인가 | 사람 + 에이전트 |
| **작업서** | `design/{슬러그}/step-*.md` | 에이전트가 그대로 실행할 단계 프롬프트 | `/design` 스킬 |

> **플랜에 코드 수준 단계를 쓰지 않는다.** 그건 `/design` 이 만든다. 마일스톤을 착수할 때 해당 `M*.md` 를 `/design` 에 넘겨 작업서로 쪼갠다.

### 왜 파일을 나눴나

한 파일에 9개 마일스톤을 다 넣으면 수백 줄이 되어 진행 추적·리뷰·머지가 전부 나빠진다. 반대로 전부 잘게 쪼개면 순서와 의존 관계가 사라진다. 그래서:

- **이 문서** = 로드맵·의존 그래프·공통 결정·진행 추적
- **M0~M4** = 개별 파일. 지금 착수 가능하고 설계 판단이 필요한 구간
- **M5~M9** = [한 파일로 묶음](M5-M9-later.md). 앞 구간 결과에 따라 내용이 바뀌므로 지금 상세화하면 낭비다

## 2. 의존 그래프

```
M0 기반 구조
 └─→ M1 코어 루프 ──→ M2 스탯·경합 ──→ M2.5 타겟팅 대역 ──→ M3 스테이지·로그라이트 ──→ M4 손님 유형
                          │                                        │                        │
                          └────────────────────────────────────────┴────────────────────────┘
                                                    ↓
                                         M5 아트·사운드 ─→ M6 메인화면·덱빌딩
                                                    ↓
                                         M7 플로우 검증 → M8 배포 → M9 QA·밸런싱
```

- **M0 은 전부의 선행 조건이다.** 어셈블리가 없으면 코드를 놓을 자리가 없다.
- **M2.5 는 M3 보다 먼저다.** M3 시너지가 "버프가 배정 우선순위를 바꾸지 않는다" 를 검증하는데, 그 배정 규칙이 곧 바뀔 거면 두 번 짜게 된다.
- M5(아트)는 M2 이후 언제든 병렬 가능하다. 로직과 파일이 겹치지 않는다.
- M9(밸런싱)는 M3 이후 계속 조금씩 돌아간다. 마지막에 몰면 늦다.

## 3. 원본 대비 변경한 것 — 반드시 확인 필요

기획 원본을 그대로 옮기지 않고 아래 4가지를 조정했다. **동의하지 않는 항목이 있으면 이 문서가 아니라 결정부터 바꿔야 한다.**

### (1) `M0` 기반 구조를 신설했다

원본은 1차 목표부터 바로 게임 로직인데, 현재 저장소는 **`Assets/Code/Scripts/` 가 비어 있고 `.asmdef` 가 하나도 없다.** 어셈블리·SO 스키마·오브젝트 풀 없이 1차를 시작하면 나중에 전부 다시 짜야 한다.

또한 **어셈블리 생성은 `CLAUDE.md` §7 사람 승인 사항**이라, 에이전트가 임의로 시작할 수 없다. M0 을 명시적 마일스톤으로 세워 승인 시점을 앞으로 당긴다.

### (2) 집기 규칙이 확정됐다 — 자격 / 배정 / 타이밍 3갈래

기획 확정에 따라 `CLAUDE.md` §1.1-3a·3b·3c 가 갱신됐다. **순차번호가 도입되어 난수가 사라졌고**, M2.5 에서 타겟팅이 대역이 되며 타이밍 갈래가 추가됐다 ([(5)](#5-타겟팅을-단일-값에서-대역으로-바꾼다-m25)).

| | 질문 | 판정 | 대역 |
|---|---|---|---|
| **자격** | 뭐라도 집을 수 있나 | 범위 ∧ 포화도 여유 ∧ 상태 | 안 씀 |
| **배정** | 누가 무엇을 가져가나 | (손님, 초밥) 쌍을 **대역 밖 거리 → 고가 → 초밥 SeqNo → 대역 폭 → 손님 SeqNo** 로 랭킹해 그리디 | 씀 |
| **타이밍** | 지금 확정하나 기다리나 | 대역 안이면 즉시 / 아니면 최선 후보의 **범위 이탈 직전** | 씀 |

- **타겟팅은 가격 대역**(`min`~`max`)이다 (TD 의 공격력 대응). 폭으로 정규화하지 않고 **폭 자체를 이산 타이브레이커**로 써서 정규화 문제를 피한다
- 4차의 "소식은 비싼 걸 우선 / 먹보는 저가를 우선" 은 **배정 우선순위**다. 더 맞는 대안이 없으면 **아무리 먼 가격도 먹는다**
- 손님 유형의 차이는 **대역의 위치와 폭**에서 나온다. 별도의 "까다로움" 스탯을 두지 않는다
- 손님이 눈앞 초밥을 **영영** 집지 않는 것은 **버그**다. 유예 중인 것은 정상이며 유한 시간 안에 끝난다
- **난수를 쓰지 않는다**: 순차번호가 모든 동률을 끝낸다. 같은 판 상태 → 항상 같은 결과
- **탐색은 이벤트 기반, 인식은 래치** (§1.1-3c) — 매 프레임 스캔 금지. 범위를 조금 벗어나도 인식된 것은 처리한다

상세 플로우와 구현 선택지는 [`.claude/domain/sushi-claim-flow.md`](../../.claude/domain/sushi-claim-flow.md).

### (3) WebGL 스모크 빌드를 8차에서 M0 으로 앞당겼다

원본은 8차에서 처음 웹에 올린다. 하지만 WebGL 은 IL2CPP + Managed Code Stripping 경로라 **거기서만 터지는 실패**(리플렉션·`JsonUtility` 관련 `MissingMethodException`)가 있다. 로직을 다 만든 뒤 발견하면 수정 범위가 커진다.

→ M0 에서 **빈 씬으로 WebGL 빌드 1회 성공**을 완료 조건에 넣고, 이후 마일스톤마다 최소 1회 재확인한다. 8차는 "실제 배포·브라우저 호환성"으로 범위를 좁힌다.

### (4) 저장/영속(persistence)이 원본에 없다

3차의 로그라이트 보상과 4차의 스테이지 진행은 **런 상태(`RunState`)를 어딘가 들고 있어야** 한다. 세션 내 메모리로 충분한지, 브라우저를 닫아도 이어서 해야 하는지에 따라 설계가 달라진다.

→ **결정 필요** (§5 열린 질문 Q1). 데모 범위에서는 "메모리 유지, 새로고침 시 초기화"가 가장 싸다.

### (5) 타겟팅을 단일 값에서 대역으로 바꾼다 (M2.5)

M2 를 실제로 돌려 보고 결정한 **기획 변경**이다. 전문은 [`M2.5-targeting-band.md`](M2.5-targeting-band.md).

| | M2 (기존) | M2.5 (변경 후) |
|---|---|---|
| 타겟팅 | 단일 가격 + 대칭 거리 | **대역(`min`~`max`)** |
| 배정 키 | 4단 | **5단** — 대역 폭(전문가 우선)이 손님 SeqNo 위에 들어간다 |
| 확정 시점 | 인식 즉시 | 대역 안이면 즉시, **대역 밖만 있으면 범위 이탈 직전** |

바꾸는 이유 둘:

- **대칭 거리가 예측되지 않는다.** 타겟팅 200 인 손님이 199 를 250 보다 먼저 집는 동작은, 플레이어에게 "200엔대를 좋아한다" 고 설명한 뒤에는 규칙으로 학습되지 않는다
- **"소식좌가 싼 걸 먼저 집는다" 의 원인은 FIFO 가 아니라 즉시 확정이다.** 매 틱 그 순간의 후보만으로 확정하므로, 싼 초밥이 먼저 들어오면 **정렬 키가 작동할 기회 자체가 없다**

**자격은 그대로다** — 대역은 자격 게이트가 **아니다.** 대신 불변식을 다시 쓴다:

> **모든 손님은 유한 시간 안에 반드시 집는다.** 대역은 *무엇을 · 언제* 를 정할 뿐, 영구 배제는 금지다.

착수 전 기준선 측정이 증상을 숫자로 확인했다 — 경합이 없는 조건에서도 타겟팅 300 인 손님이 먹은 것의 **81%가 300 미만**이었다 ([`design/m2-5-targeting-band/baseline.md`](../../design/m2-5-targeting-band/baseline.md)).

구현 중 결정·발견한 것 셋:

- **래치를 이탈 시각 기준으로 바꿨다.** 인식 기준으로 재면 `래치 ≥ 범위 통과 시간` 일 때만 의도와 맞는데 stage01 이 그 조건을 어겼다(통과 3.0초 / 래치 1.0초). 바꾸면 마감시한이 만료보다 항상 먼저 와서 **불변식이 밸런스 값과 무관해진다**
- **새 구성 제약**: `자리 좌표 + Reach < 벨트 길이`. 어기면 기다리는 손님의 초밥이 범위를 벗어나기 전에 끝점에서 사라진다. 즉시 확정이던 M2 까지는 없던 조건이다
- **대칭성은 대역 밖에 남아 있다.** 없앤 것은 대역 *안* 의 비대칭 선호뿐이다

마감시한은 **기하로 계산된다** (`ReachWindow.ExitSeconds`). 유예 시간 SO 필드를 새로 두지 않는다.

## 4. 공통 규칙 (모든 마일스톤에 적용)

각 `M*.md` 에서 반복하지 않는다. 여기만 본다.

- **TDD 기본값** — 순수 로직은 실패 테스트 → 최소 구현 → 리팩터. EditMode 전량 통과가 커밋 게이트 (`CLAUDE.md` §5·§8)
- **밸런스 수치는 전부 SO 필드.** 이 플랜 문서들은 **필드 이름만 정하고 값은 정하지 않는다.** 값은 사람이 정한다 (`CLAUDE.md` §3.1·§7)
- **로직은 `MonoBehaviour` 밖** 순수 C# 클래스에 (`CLAUDE.md` §3.2)
- **초밥 인스턴스는 `SushiPool` 경유.** `Instantiate`/`Destroy` 직접 호출 금지 (§3.4)
- **어셈블리 의존은 단방향** — `Runtime.Data ← Runtime ← Presentation` (§3.7)
- **브랜치**: 마일스톤 안의 작업 단위마다 `feat/*` → PR → 사람 승인 (§6)
- **§7 승인 항목**(새 어셈블리·새 패키지·`ProjectSettings`·밸런스 일괄 수정)이 나오면 그 자리에서 멈추고 물어본다

## 6. 진행 추적

마일스톤이 끝나면 이 문서 §1 표의 상태를 갱신하고, 해당 `M*.md` 의 완료 판정 체크박스를 채운다.

```
☐ 미착수   ◐ 진행 중   ☑ 완료
```

새로 알게 된 **이 프로젝트만의 설계 지식**은 플랜이 아니라 `.claude/domain/` 으로 승격한다 (`/task-done` STEP 5). 플랜은 "무엇을 할 것인가", 도메인 문서는 "왜 이렇게 돌아가는가"다.
