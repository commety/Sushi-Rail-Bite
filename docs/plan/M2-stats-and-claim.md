# M2 — 스탯 · 배정 · 경제 (원본 2차)

> 원본 목표: *"초밥은 가격과 포화도를 가진다 / 타워는 초밥을 스캔해서 자신의 우선순위에 따른 초밥을 우선적으로 처리한다 / 타워는 집기 범위, 먹는 시간, 소화 시간을 가진다"*

## 이 마일스톤이 §1.1-3a 전체를 완성한다

M1 에서 자격 판정과 이벤트 구조를 세웠다면, M2 는 그 위에 **배정**을 얹고 **스테이지 제한·경제**를 도입한다.

| | 판정 | M1 대비 |
|---|---|---|
| **자격** | 범위 ∧ 포화도 여유 ∧ 상태. **가격 안 봄** | 그대로 |
| **배정** | (손님, 초밥) 쌍을 **`−\|가격−타겟팅\|` → 고가 → 초밥 SeqNo → 손님 SeqNo** 로 랭킹해 그리디 확정 | **신규** |

**케이스별로 코드를 나누지 않는다.** 기획의 세 경우(1:N / N:1 / N:M)는 위 정렬 규칙 하나로 전부 덮인다. 나눠 짜면 경계에서 반드시 어긋난다.

### 난수를 쓰지 않는다

순차번호가 모든 동률을 끝낸다. **난수원 주입도, 시드 고정도 필요 없다.** 같은 판 상태는 항상 같은 결과를 낸다 — 플레이어에게 일관적이고, 테스트가 단순해진다.

상세: [`sushi-claim-flow.md`](../../.claude/domain/sushi-claim-flow.md) · 데이터: [`data-model.md`](../../.claude/domain/data-model.md)

## 스폰 구성 — 덱에서 벨트로

가격이 생기는 마일스톤이라 **어떤 초밥이 얼마나 자주 벨트에 오르는지**도 여기서 정해진다. 목표는 하나다:

> 플레이어가 구성한 덱 안에서 **비쌀수록 적게 · 쌀수록 많이** 나온다. 다만 비싼 카드도 제 주기로는 반드시 나온다.

### 가방이 아니라 수열이다

풀에 인스턴스를 몇 개씩 담아 두는 방식(가방)은 **쓰지 않는다.** 가중치 합과 인스턴스 개수가 정수에서 어긋나고(가중합 10인데 인스턴스는 8개), 남는 칸을 채우는 규칙이 휴리스틱이 되며, 그 휴리스틱이 결국 난수를 부른다.

**원하는 것은 재고량이 아니라 시간당 등장 빈도**다. 그래서 배출 수열로 표현한다.

```
덱(유형 목록)  →  가격에서 share 계산  →  결정적 배출 수열  →  벨트
```

**풀 크기는 구성 규칙이 아니다.** `SushiPool` 의 프리웜 개수(성능 힌트)로만 남는다. 벨트 밀도는 `SpawnIntervalSeconds`·`BeltSpeed`·`BeltLength` 가 이미 정하므로 풀에 상한을 두지 않는다 — 두면 밀도 손잡이가 둘로 늘어 서로 간섭한다.

> 덱빌딩 화면은 M6 다. 그때까지는 `StageConfig.SpawnTable` 이 덱 대역으로 쓰인다.

### share 계산 — 확정됨

```
share_i  ∝  (minPrice / price_i) ^ α
```

| 항목 | 결정 |
|---|---|
| `α` | **1.0** — `StageConfig` 필드라 스테이지마다 조절 가능 |
| `minPrice` | **덱 안 최저가**. 스테이지 스폰 테이블 전체나 전역 최저가가 아니다 |
| 수열 상태 | **스테이지 시작마다 리셋** |

- **가격 비율만 쓴다.** `price / 10` 같은 절대 스케일이 아니라서 100엔이든 1000엔이든 동일하게 동작하고, 별도 정규화가 필요 없다
- **α = 1.0 은 "유형별 매출 기여가 균등" 한 지점**이다 (`price × share` 가 상수). 비싼 초밥은 적게 나오지만 한 방이 크다 — 총량으로는 이득도 손해도 아니고, 존재 의의는 **타겟팅이 높은 손님을 먹일 유일한 수단**이라는 데 있다. 더 희소하게 만들려면 α 를 올린다 (M9 밸런싱의 손잡이)
- **덱이 바뀌면 기존 카드의 등장률도 바뀐다.** `minPrice` 가 덱 기준이라 그렇다. 이건 **버그가 아니라 설계 목표**다 — 비싼 카드를 넣으면 나머지가 상대적으로 흔해지는 것이 덱빌딩의 의미다

**예시** (장어 300 · 방어 150 · 연어 120 · 한치 100 · 광어 100, α = 1.0)

| 유형 | share | 24개 구간 등장 | 구간 매출 |
|---|---|---|---|
| 장어 | 8.7% | 2 | 600 |
| 방어 | 17.4% | 4 | 600 |
| 연어 | 21.7% | 5 | 600 |
| 한치 | 26.1% | 6 | 600 |
| 광어 | 26.1% | 6 | 600 |

### 배출 순서 — 난수 없음

매 스폰마다:

```
각 유형에 credit_i += share_i
credit 이 가장 큰 유형을 배출        ← 동률이면 덱 순서 (결정적)
그 유형의 credit -= 1
```

share 가 0.5 / 0.25 / 0.25 면 `A B C A | A B C A | …` 가 나온다. 비율은 정확히 2:1:1 이고 **고르게 흩어진다.**

이 성질이 요구사항을 직접 만족시킨다:

- **비싼 초밥이 앞에 뭉치지 않는다.** share 가 낮은 유형은 credit 이 차는 데 시간이 걸려 제 주기대로만 나온다 → 초반이 자연히 싼 쪽으로 기운다
- **초반 억제 장치(nice value 류)를 넣지 않는다.** 그건 무작위 구성이 비싼 것을 앞에 몰아넣는 문제를 사후에 고치는 장치인데, 여기서는 애초에 몰리지 않는다. 넣으면 α 와 손잡이가 겹쳐 조절만 어려워진다
- **난수 0** — 같은 덱·같은 스테이지는 항상 같은 수열. 배정과 같은 결정성 기준을 공유한다
- 정수 나눗셈이 없어 **가중합과 인스턴스 개수가 어긋날 자리가 없다**

`credit` 배열은 생성자에서 한 번 잡고 스폰마다 재사용한다 — `Update` 경로 할당 0 (`CLAUDE.md` §4.3, 배포 타깃이 WebGL).

## 완료 판정

**스탯·배정**
- [ ] 초밥이 `SushiData` 에서 가격·포화도를 읽는다 (코드 상수 0)
- [ ] 초밥이 스폰 시 **순차번호**를 발급받는다
- [ ] 손님이 `CustomerData` 에서 집기 범위·타겟팅·먹는 시간·최대 포화도·소화 시간·영입 비용을 읽는다
- [ ] 손님이 배치 시 **순차번호**를 발급받는다
- [ ] 먹는 데 시간이 걸린다 (즉시 소비 아님)
- [ ] 포화도가 차면 소화 상태로 전이하고, 소화가 끝나면 다시 먹는다
- [ ] **타겟팅에서 아무리 먼 초밥도, 더 맞는 대안이 없으면 먹는다**
- [ ] 범위 안 초밥이 여러 개면 **타겟팅에 가장 가까운 것**을 집는다
- [ ] 거리가 같으면 **비싼 쪽**을 집는다 (타겟팅 200 → 190 vs 210 이면 210)
- [ ] 거리·가격이 같으면 **초밥 SeqNo 낮은 것**
- [ ] 한 초밥을 둘 이상이 노리면 **타겟팅이 가까운 손님**이 가져가고, 동거리면 **손님 SeqNo 낮은 쪽**
- [ ] **같은 판 상태를 두 번 배정하면 결과가 완전히 같다** (결정성)
- [ ] **프로덕션 배정 경로에 `Random` 이 0건이다**
- [ ] 한 초밥이 두 손님에게 배정되지 않는다 (상태 필드로 방지)
- [ ] `Grep "Targeting"` 결과가 **자격 판정 경로에 없다**
- [ ] 이벤트 기반 구조 유지 — `Update` 내 손님×초밥 전수 순회 0건

**스폰 구성**
- [ ] 벨트에 오르는 초밥 유형이 **덱에 있는 것만**이다
- [ ] 유형별 등장 비율이 `(minPrice / price) ^ α` 에 비례한다 (`α` 는 `StageConfig` 에서 읽는다 — 코드 상수 0)
- [ ] `minPrice` 를 **덱 안에서** 구한다
- [ ] 가격을 전부 10배로 키워도 **share 가 변하지 않는다** (비율만 쓴다는 것의 검증)
- [ ] α = 1.0 에서 **유형별 매출 기여가 균등**하다
- [ ] share 가 낮은 유형이 **첫 구간에 몰리지 않는다** (고른 분산)
- [ ] 같은 덱·같은 스테이지를 두 번 돌리면 **배출 수열이 완전히 같다**
- [ ] **프로덕션 스폰 경로에 `Random` 이 0건이다**
- [ ] 수열 상태가 **스테이지 시작 시 리셋**된다
- [ ] `SushiSpawnEntry` 에 손으로 적는 가중치 필드가 **없다** (share 는 가격에서 유도된다)
- [ ] 풀 크기가 **구성에 관여하지 않는다** — 프리웜 개수로만 쓰인다

**스테이지 제한·경제**
- [ ] 한 스테이지의 **최대 배치 손님 수**가 `StageConfig` 에서 오고 강제된다
- [ ] 스테이지 시작 시 **초기 영입 예산**이 지급된다
- [ ] 초밥 처리 시 **영입 재화가 `점수/10` 만큼** 누적된다
- [ ] 영입 비용이 모자라면 배치되지 않는다

- [ ] EditMode 전량 Green + `/run webgl` 유지

## 산출물

### `Runtime.Data`

M0 에서 만든 스키마에 값을 채운다. **값은 사람이 정한다** (§7). 에이전트는 필드와 검증만.

스키마 변경 2건:

| 대상 | 변경 |
|---|---|
| `StageConfig` | 희소성 지수 `α` 필드 **추가**. 기본값 1.0, 하한 0 |
| `SushiSpawnEntry` | `Weight` 필드 **제거** → `SushiData` 참조만 남는 덱 슬롯이 된다 |

> `Weight` 를 남기면 안 된다. share 가 가격에서 유도되므로 손으로 적은 가중치는 **가격과 어긋나는 두 번째 진실**이 되고, 둘이 갈라지는 순간 어느 쪽이 맞는지 판정할 방법이 없다.

### `Runtime`

| 타입 | 책임 |
|---|---|
| `SpawnShareTable` | 덱 + α → 유형별 share. **가격을 읽는 곳**. `minPrice` 는 덱 안에서 |
| `SpawnSequence` (확장) | credit 누적 → 배출. 난수 없음, 동률은 덱 순서. 스테이지 시작 시 리셋 |
| `TargetingPriority` | `−\|가격 − 타겟팅\|` 계산. 타겟팅은 **단일 값** |
| `SushiClaimResolver` | (손님, 초밥) 쌍 랭킹 → 그리디 배정. **타겟팅을 읽는 곳** |
| 순차번호 발급기 | 초밥 스폰·손님 배치 시 단조 증가 번호 |
| 손님 상태 머신 | `Idle → Eating → Full/Digesting → Idle`. 전이는 순수 클래스 |
| `CustomerRuntimeState` | 현재 포화도, 남은 소화 시간, 먹는 중인 초밥, SeqNo. **SO 와 분리** |
| 영입 재화 집계 | `점수/10` 누적, 배치 시 차감, 잔액 검사 |
| 배치 제한 검사 | 최대 배치 손님 수 |

> `IRandomSource` 는 **필요 없다.** 배정은 순차번호가, 스폰은 credit 수열이 동률을 끝낸다 — 두 경로 모두 난수가 없다. 난수원 주입도 시드 고정도 하지 않는다. → [`.claude/rules/tests.md`](../../.claude/rules/tests.md) §5

## 작업 순서

1. **SO 필드 확정** (`Runtime.Data`) — 값은 비워두고 스키마·검증만
2. **순차번호 발급** (`Runtime`) — 초밥 스폰·손님 배치 시
3. **우선순위 계산** (`Runtime`) — `TargetingPriority`. 산정식 **확정됨**
4. **배정기** (`Runtime`) — 쌍 랭킹 → 그리디. 결정성 테스트 포함
5. **스폰 구성** (`Runtime`) — share 계산 → credit 배출 수열. 결정성·분산 테스트 포함
6. **먹는 시간·포화도** (`Runtime`) — 실패 테스트 → 구현
7. **소화 상태 머신** (`Runtime`) — 전이 조건 테스트 우선
8. **경제** (`Runtime`) — 영입 재화 누적·차감, 배치 제한
9. **벨트/손님 연결** — 이벤트 경로 배선
10. **View 반영** (`Presentation`) — 먹는 중·소화 중, 잔액·배치 수 표시

2·3 이 4 의 선행. 5·6·7·8 은 서로 독립이라 병렬 가능하다. 5 는 1(가격 필드)만 있으면 시작할 수 있다.

## 리스크

| 리스크 | 대응 |
|---|---|
| **타겟팅이 자격 게이트로 새어 들어감** | 이 마일스톤 최대 위험. 완료 판정에 grep 조건을 넣어 둔 이유다. `/qa` 의 "타겟팅 자격 오용" 검사 실행 |

| 난수가 다시 들어옴 | 결정성 테스트(`Resolve_SameBoardTwice_...` · `Emit_SameDeckTwice_...`)가 회귀 방지선. preflight 의 `Random.` 금지 검사가 함께 잡는다 |
| **스폰 구성이 가방 방식으로 되돌아감** | 가중합과 인스턴스 개수가 어긋나고 남는 칸이 난수를 부른다. 수열 방식을 유지한다 |
| 초반 억제 장치(nice value 류)를 덧붙임 | 고른 분산이 이미 해결한다. 덧붙이면 α 와 손잡이가 겹쳐 조절이 어려워진다 |
| **소식 손님(M4)이 굶는다** | 타겟팅이 높은데 비싼 초밥이 희소하면 대기가 길어진다. 구경이 아니라 버그는 아니지만 소식 손님의 체감 가치가 α 에 직결된다 — M4 착수 시 함께 본다 |
| 한 초밥이 두 손님에게 배정됨 | 배정 확정 ~ 소비 완료 사이 구간. `Claimed` 상태 필드로 방지 |
| 밸런스 수치를 에이전트가 임의로 채움 | §7 위반. 필드만 만들고 값은 사람에게 |

## 열린 질문

**배정 산정식은 확정됐다** — 단일 값 + 거리 + 동거리 고가 우선. 더 이상 블로커가 아니다.

**스폰 구성도 확정됐다** — share = `(덱 내 최저가 / 가격) ^ α`, α 기본값 1.0, 수열은 스테이지 시작마다 리셋, 난수 없음.

남은 것은 **작업 중 에이전트가 사람에게 질문해서 정한다.** 지금 정하지 않는다.

| # | 질문 | 비고 |
|---|---|---|
| 1 | `점수/10` 의 정수/실수·반올림 규칙, 잔여분 누적 여부 | 제안: 실수 누적, 표시할 때만 버림 ([`data-model.md`](../../.claude/domain/data-model.md) §4) |
| 2 | 순차번호 범위 — 스테이지마다 리셋? 런 전체 연속? | 기본안: 스테이지 리셋 |
| 3 | 인식 래치에 상한을 둘지 | 없으면 한참 지나간 초밥까지 집는 그림 |
| 4 | 한 손님이 동시에 여러 초밥을 집을 수 있나 | 기본안: 아니오, 한 번에 하나 |
| 5 | 영입 재화가 스테이지 간 이월되나 | M3 의 보상 설계와 연결 |
