# M4 — 손님 유형과 스테이지 진행 (원본 4차)

> 원본 목표: *"기본 손님: 모든 스탯이 평이하다 / 소식 손님: 포화도가 적지만 비싼 걸 우선적으로 고른다, 영입 비용 중간 / 먹보 손님: 먹는 속도가 빠르고 포화도가 높지만 저가를 우선적으로 고른다, 영입 비용이 비싸다 / 스테이지가 끝나면 다음 스테이지로 넘어간다"*

## "고른다" 가 적용되는 지점

원본의 "우선적으로 고른다" 는 **배정(§1.1-3a)** 에서 작동한다. **자격에는 관여하지 않는다.**

| 유형 | 원본 표현 | 실제 동작 |
|---|---|---|
| 소식 | 비싼 걸 우선 | 타겟팅 값이 **높다**. 범위에 여러 개면 비싼 쪽을 집고, 경합 시 비싼 초밥에서 우선순위가 높다. **범위에 싼 것 하나뿐이면 그걸 먹는다** |
| 먹보 | 저가를 우선 | 타겟팅 값이 **낮다**. 범위에 여러 개면 싼 쪽을 집고, 경합 시 싼 초밥에서 우선순위가 높다. **범위에 비싼 것 하나뿐이면 그걸 먹는다** |

**유형 차이는 코드가 아니라 `CustomerData` 값의 차이다.** M2 에서 만든 로직 하나가 세 유형을 전부 처리해야 한다. 유형별 `if` 분기나 상속 클래스가 생기면 설계 실패다.

> 기획 갱신으로 "중간 정도 / 비싸다" 가 **영입 비용**임이 확정됐다.

## 선행 조건

- M3 완료 (보상으로 손님을 영입하려면 보상 시스템이 있어야 한다)

## 완료 판정

- [ ] 기본·소식·먹보 3종이 **`CustomerData` 애셋 3개**로 존재한다
- [ ] 세 유형이 **같은 `CustomerLogic` 코드 경로**를 탄다 (유형별 분기·상속 0)
- [ ] 소식 손님이 **범위에 저가 초밥 하나뿐일 때** 그것을 먹는다 (자격 통과 확인)
- [ ] 먹보 손님이 **범위에 고가 초밥 하나뿐일 때** 그것을 먹는다
- [ ] 소식 손님이 **범위에 고가·저가가 같이 있으면** 고가를 집는다 (선택 확인)
- [ ] 먹보 손님이 **범위에 고가·저가가 같이 있으면** 저가를 집는다
- [ ] 손님 영입 비용이 데이터로 있고 보상 화면에 반영된다
- [ ] 스테이지 클리어 후 다음 스테이지로 넘어간다 (3스테이지 연결)
- [ ] 마지막 스테이지 클리어 시 런이 종료된다
- [ ] EditMode 전량 Green + `/run webgl` 유지

## 산출물

### `Runtime.Data` — 밸런스 애셋 (값은 사람이 결정)

| 애셋 | 특징 |
|---|---|
| `Customer_Basic` | 기준값. 다른 둘의 비교 기준 |
| `Customer_Light` (소식) | 최대 포화도 ↓, 타겟팅 값 높음, 영입 비용 중간 |
| `Customer_Glutton` (먹보) | 먹는 속도 ↑, 최대 포화도 ↑, 타겟팅 값 낮음, 영입 비용 높음 |

`StageConfig` 3종 (데모 3스테이지)도 여기서 채운다.

### `Runtime`

- 스테이지 진행 — 현재 스테이지 → 다음 스테이지 전이, 런 종료 판정
- `RunState` 확장 — 보유 손님 목록, 진행 인덱스

### `Presentation`

- 손님 유형별 View 구분 (색·라벨 수준. **아트는 M5**)
- 스테이지 전환 화면

## 작업 순서

1. **`CustomerData` 애셋 3종** — 값은 사람 승인 후 입력
2. **동일 코드 경로 검증** — 유형별 분기 없이 세 애셋이 다르게 동작하는지 테스트
3. **영입 비용** — M2 의 경제 시스템에 유형별 비용 반영
4. **스테이지 진행** (`Runtime`) — 다음 스테이지 전이, 런 종료
5. **전환 화면** (`Presentation`)

1~2 는 사실상 "데이터만 넣고 테스트" 라 가볍다. 무거운 쪽은 4.

## 테스트 항목

| 대상 | 테스트 이름 예시 |
|---|---|
| 자격 — 소식이 저가만 있을 때 | `CanTake_LightCustomerOnlyCheapSushi_ReturnsTrue` |
| 자격 — 먹보가 고가만 있을 때 | `CanTake_GluttonOnlyExpensiveSushi_ReturnsTrue` |
| 배정 — 소식은 비싼 쪽 | `Resolve_LightCustomerMixedPrices_TakesExpensive` |
| 배정 — 먹보는 싼 쪽 | `Resolve_GluttonMixedPrices_TakesCheap` |
| 배정 — 유형별 승자 | `Resolve_ExpensiveSushiLightVsGlutton_LightWins` |
| 배정 — 반대 | `Resolve_CheapSushiLightVsGlutton_GluttonWins` |
| 포화도 차이 | `Eat_GluttonVsLight_GluttonEatsMoreBeforeFull` |
| 스테이지 전이 | `Advance_StageCleared_MovesToNextStage` |
| 런 종료 | `Advance_LastStageCleared_EndsRun` |

**앞의 자격 테스트 2개가 이 마일스톤의 핵심 방어선이다.** 유형이 생기는 순간 "소식은 싼 걸 안 먹어야 하지 않나?" 라는 오해가 코드로 들어가기 쉬운데, 이 테스트가 그걸 막는다. 배정 테스트 2개는 유형이 **실제로 체감되는지**를 보장한다.

## 리스크

| 리스크 | 대응 |
|---|---|
| **유형별 `if` 분기·상속 클래스가 생김** | 완료 판정에 "동일 코드 경로" 를 넣은 이유. 유형은 데이터 차이여야 한다 |
| "우선적으로 고른다" 를 필터로 재도입 | 완료 판정의 자격 테스트 2개가 방어선 |
| 밸런스 3종을 에이전트가 임의로 채움 | §7 위반. 값은 사람이 |
